# Tracking QC Playbook

用于上线后或联调阶段，检查 Tracking Plan 与实际上报数据是否一致。

## 什么时候读

- 用户问“埋点接好了吗”
- 用户要做 Tracking Plan 质检
- 用户要按某个数据源或某个 Pipeline 核对上报情况

## 执行步骤

1. 确认项目与计划
   先拿到 `project_id`，再明确 `plan_id`。
   如果用户没指定计划，先用 `list_tracking_plans`。

2. 确认计划状态
   质量检查通常以已发布计划为基线。
   如果计划还没发布，先说明限制，再让用户决定是否继续推进到发布。

3. 确认前置验证
   先确认用户已经自行完成：
   - 重启 / 重新部署让埋点代码生效
   - 基本功能回归
   - 至少看到关键事件已正常触发
   若用户尚未完成，不进入质检，先引导用户完成这些动作。

4. 确认检查范围
   使用 [../../wave-tracking-common/prompts.md](../../wave-tracking-common/prompts.md) 中的 `P-质检·范围`。
   再调用 `get_tracking_plan_quality_check`。

5. 解释结果
   输出时按“可执行问题清单”整理，而不是只贴原始状态：
   - 缺失事件
   - 缺失属性
   - 已上报但值不符合计划
   - 仅部分实现
   - 最近数据质量异常

6. 必要时交叉验证
   可补充使用：
   - `list_events`
   - `list_event_properties`
   - `list_pipelines`

## 辅助规则

- 先给结论，再给证据。
- 问题要落到“哪个事件/哪个属性/哪类端需要改”。
- 如果用户需要进一步查实时行为或做原因分析，切换到 `wave-analytics`。
- 质检不是“代码写完就立刻跑”的步骤，应该在用户确认事件已实际触发后再进行。
