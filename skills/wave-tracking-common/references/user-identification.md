# User Identification

本文件用于整理登录、注册、登出、跨设备、共享设备、匿名转登录等场景下的用户标识设计规则。
只在这些场景出现时按需读取。

## 1. 为什么这是单独主题

用户标识不是普通埋点细节，而是分析准确性的基础：

- 登录前后行为是否能打通
- 跨设备行为是否能归到同一用户
- 共享设备是否会把不同人混成一个用户
- 漏斗、留存、用户数统计是否可信

所以只要场景里有登录态变化，就不要只讲事件设计，必须同时明确 identify 方案。

## 2. 三个核心 ID

- `anon_id`
  匿名 ID，标识设备或浏览器。通常由客户端 SDK 自动生成并保存在本地。
- `login_id`
  登录 ID，标识业务用户。应使用稳定、全局唯一、不可变的业务主键。
- `ssid`
  服务端基于 `anon_id` / `login_id` 计算出的唯一用户 ID。分析时最终以它识别唯一用户。

简化理解：

- 未登录阶段主要靠 `anon_id`
- 登录后主要靠 `login_id`
- Wave 在服务端把它们统一归并到 `ssid`

## 3. identify 的作用

`identify` 的核心作用是把“当前设备上的匿名用户”与“登录用户”关联起来。

结果是：

- 登录前匿名行为与登录后行为会被自动归到同一用户
- 新设备登录后也能归到同一登录用户
- 历史数据不会因为清 Cookie、换设备而丢失

## 4. 客户端场景

### 登录成功后

- 应立即调用 `identify(login_id)`
- `identify` 会自动生成 `$Identity` 事件
- 如需记录登录方式、登录入口，可额外记录业务事件 `UserLogin`

顺序要求：

1. 先 `identify`
2. 再记录登录后的业务事件

不要反过来，否则登录事件会带着旧身份信息。

### 登出时

- 一般调用 `reset()`
- 公共设备场景才考虑 `reset(true)`，即同时重置匿名 ID

### 不推荐做法

- 未登录时调用 `identify`
- 每次页面刷新都重复 `identify`
- 使用 session id、token、会变化的手机号作为 `login_id`

## 5. 服务端场景

服务端 SDK 不能自动拿到客户端匿名 ID，所以要特别说明：

- 纯匿名事件：客户端把 `anon_id` 传给服务端，再上报
- 已登录事件：直接带 `login_id`
- 登录关联事件：必须同时提供 `anon_id` 和 `login_id`

关键差异：

- 客户端 SDK：调用 `identify()` 会自动完成身份关联
- 服务端 SDK：需要显式调用 `Identify()`，并同时设置 `AnonID` 与 `LoginID`

所以，如果用户要“把登录事件放在服务端打”，你必须额外确认：

1. 客户端是否把 `anon_id` 传给服务端
2. 服务端是否真的调用了身份关联方法，而不是只发了一个普通登录事件

## 6. 典型业务场景

### 匿名浏览后注册登录

这是最典型的 identify 场景：

- 匿名浏览商品
- 加购
- 注册/登录
- 下单

这里必须在登录成功时调用 `identify`，否则注册前行为和购买行为会断开。

### 多设备登录

同一用户在手机、电脑、平板登录时，多个设备上的行为都应归到同一 `login_id`。
如果不同端用了不同的用户标识，会被识别为不同用户。

### 共享设备

例如家庭共用 iPad：

- 用户 A 登录后使用
- 登出
- 用户 B 再登录

这里一定要在登出时正确 `reset()`，否则后续归属容易混乱。

### 公共设备

例如商场体验机、门店自助机：

- 需要在登出时使用 `reset(true)`
- 让下一个用户拿到全新的匿名 ID

## 7. login_id 选择原则

推荐：

- 数据库主键
- 不可变 UUID
- 全局唯一账号 ID

不推荐：

- session id
- access token
- 会变化的手机号
- 不同平台各自维护的不同 ID

如果邮箱、手机号会变化，把它们作为用户属性，不要直接做 `login_id`。

## 8. 对 AI 的执行要求

当用户提到以下任一场景时，必须主动补充用户标识设计，而不是只给埋点事件表：

- 登录 / 注册
- 登出
- 匿名用户转登录用户
- 第三方登录
- 跨端 / 跨设备
- 公共设备 / 共享设备
- 留存、漏斗、用户数明显不准

至少要回答四个问题：

1. `login_id` 用什么字段
2. 客户端何时调用 `identify`
3. 登出是否需要 `reset` 或 `reset(true)`
4. 服务端是否需要接收并透传 `anon_id`

## 9. 推荐输出格式

如果 identify 是关键问题，输出里单独加一个“用户标识方案”段落，至少包含：

- `login_id` 来源
- `anon_id` 来源
- 客户端登录后调用点
- 登出调用点
- 服务端是否参与身份关联
- 风险点：重复 identify、漏 reset、使用不稳定 ID
